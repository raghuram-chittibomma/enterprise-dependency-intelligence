# AGENTS.md — Instructions for AI Coding Agents

This file gives any AI coding agent (Cursor, Claude, Copilot, etc.) the operating rules for working in this repository. Read this before making changes.

## Project in one paragraph

Enterprise Dependency Intelligence is a knowledge-graph-backed application that lets architects, TPMs, and engineers discover how a fictional enterprise's (Meridian Retail Group) applications, APIs, services, databases, pipelines, and business capabilities depend on each other — with every answer traceable to graph evidence and its source system. MVP1 (current milestone) answers this with deterministic Cypher queries and zero LLM calls; MVP2+ layers Graph RAG, hybrid document retrieval, and bounded agentic investigation on top of the same graph without requiring a rebuild. See `docs/00_project/PROJECT_CHARTER.md` and `docs/00_project/PRODUCT_BRIEF.md`.

## Golden rules

1. **Delivery tracking is local-only for MVP1, not GitHub-first.** This is a deliberate, recorded deviation from the default — see `docs/00_project/AI_ORCHESTRATOR_BRIEF.md`'s Assumptions section. Work proceeds as direct commits to `main` on a local git repo, tracked via the agent's todo list (increment IDs referenced in `docs/00_project/PRODUCT_BRIEF.md`'s FR table), not GitHub issues/PRs. Local docs remain the durable artifacts (architecture, ADRs, strategy, briefs, runbook, release notes) regardless.
2. **Synthetic data only.** All source data (CMDB, API Catalog, DB Metadata, Team Ownership, Integration Catalog) describes the fictional "Meridian Retail Group" scenario, generated by `src/datagen/`. Never ingest, reference, or commit real company, customer, or personal data.
3. **Build-time SDLC agents are not runtime product components.** Enterprise agent roles (Product Analyst, Solution Architect, Implementation Planner, Test/Eval Designer, Code Reviewer, Refactor Reviewer, Documentation Agent, Release Manager, Dependency Upgrade Agent) are served by the **Enterprise SDLC MCP** server — not part of this repo's own source tree. Runtime components live under `src/` — see `docs/01_architecture/ARCHITECTURE.md`.
4. **Zero LLM calls in the MVP1 critical path.** Search, detail, traversal, path-finding, ownership, capabilities, NL query, and evidence are all deterministic graph queries (see `ADR-0004-deterministic-nl-query-layer.md`). Every dependency claim must trace to an actual graph path with a source — never state a relationship that isn't backed by an edge in the graph. LLM reasoning is reserved for MVP2+ (Graph RAG) and must go through the `answer_generator` extension point, not be added ad hoc into MVP1 query paths.
5. **One agent modifies code per implementation slice**, unless a task explicitly says otherwise. Avoid touching files outside the scope of the current increment.
6. **Every change traces back to an increment** in the todo list / `docs/00_project/PRODUCT_BRIEF.md` FR table. Commit messages should reference the increment (e.g. `increment-6-search: add fuzzy entity search endpoint`).
7. **Tests/evals are part of the definition of done.** New runtime behavior needs corresponding tests under `tests/` and, where relevant, golden-dataset scenarios under `evals/`.
8. **Every significant technical decision gets an ADR** under `docs/01_architecture/DECISIONS/` (see that folder's `README.md` for the format). Never rewrite ADR history — supersede instead.

## Enterprise SDLC MCP (build-time agents and skills)

Generic build-time agent roles and SDLC skills are **not** duplicated locally. Fetch them from the Enterprise SDLC MCP server configured in `.cursor/mcp.json`:

| Need | MCP call |
|------|----------|
| List agents (+ `permissions`) | `list_agents` |
| Agent role definition | `get_agent("<id>")` — e.g. `code-reviewer`, `solution-architect` |
| List skills (+ `applies_when`) | `list_skills` |
| Generic SDLC checklist | `get_skill("<id>")` — e.g. `pr-code-review`, `architecture-review` |
| Domain-specific checklist | `get_project_skill("<filename>")` from project overlay (`.skills/`) |
| Parsed project manifest | `get_project_manifest` |
| Manifest gap check | `validate_manifest` — run this once after initial setup and after every catalog upgrade |
| Launch independent review | Prompt `independent_code_review` |
| Launch architecture review | Prompt `architecture_review` |
| Launch any agent + skill combo | Prompt `launch_role("<agent-id>", "<skill-id>,...", "<context>")` |

Project manifest: `sdlc.project.yaml` (resolves `{{project.*}}` placeholders in catalog templates).

## Where things live

- `docs/00_project/` — project initiation brief, charter, product brief.
- `docs/01_architecture/` — architecture, data model, ADRs.
- `docs/02_testing/` — test strategy, evaluation strategy.
- `docs/03_operations/` — runbook, release notes.
- `src/` — runtime application code only (datagen, ingestion, graph, nlquery, api, web).
- `tests/`, `evals/` — test and evaluation code (golden dataset lives under `evals/`).
- `data/sample/` — generated synthetic source datasets (CMDB, API Catalog, DB Metadata, Team Ownership, Integration Catalog); regenerable, never hand-edited real data.
- `.skills/` — **project overlay only** (this project's own domain-specific checklists — never duplicate catalog agent/skill definitions here).
- `sdlc.project.yaml` — project manifest for MCP placeholder resolution.
- Enterprise SDLC MCP server and catalog — standalone repo [`enterprise-sdlc-mcp`](https://github.com/raghuram-chittibomma/enterprise-sdlc-mcp), installed editable into this repo's own `.venv`. Not vendored here.

## Before committing

- Confirm the change maps to an increment in the todo list / `docs/00_project/PRODUCT_BRIEF.md` FR table.
- Run the test suite and ensure it passes.
- Update relevant docs under `docs/` if architecture, data model, or operational behavior changed.
- Reference the increment ID in the commit message.

## Before calling an increment done

- Do not just eyeball your own diff. For anything touching the ontology, graph queries, or the deterministic/LLM boundary, run it past the Solution Architect's checklists (`knowledge-graph-modeling-review`, `architecture-review`) via **Enterprise SDLC MCP** before moving on to the next increment.
- At minimum: call MCP `get_skill("pr-code-review")` and self-apply its checklist to the diff even without a formal PR, given the `local_only` delivery-tracking decision (see `docs/00_project/AI_ORCHESTRATOR_BRIEF.md`).
- At release readiness (increment-15), run a full independent Code Reviewer and Refactor Reviewer pass (fresh-context subagents via MCP) over the accumulated `src/` tree before declaring MVP1 done — this is the one point where the `local_only` decision still gets an independent-review gate.
