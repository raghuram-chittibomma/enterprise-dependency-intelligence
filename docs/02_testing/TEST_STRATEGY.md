# Test Strategy

Status: accepted

Read by: Test/Eval Designer Agent, Code Reviewer Agent, `test-eval-design` skill.

## Test levels

| Level | What it covers | Location | Runs when |
|-------|-----------------|----------|-----------|
| Unit | Source parsers (one per MVP1 source), entity resolution (all 4 resolution steps in `ADR-0002`), Cypher query template builders, NL query intent classification, answer string templates. | `tests/unit/` | Every commit |
| Integration | End-to-end ingestion (source file → resolved, provenance-tagged graph) against a real (or fallback) graph store; API routes for search/detail/traversal/paths/ownership/capabilities/NL query against a seeded graph. | `tests/integration/` | Every commit |
| Data quality | Automated graph invariants: no orphan nodes, no duplicate natural keys, referential consistency (every relationship endpoint resolves to an existing node), no node/relationship missing required provenance fields. | `tests/quality/`, CLI at `src/quality/run.py` | After every ingestion run; every commit touching ingestion or the ontology |
| Golden dataset (eval) | The 7 supported NL questions, plus representative FR1–FR10/FR12/FR13 scenarios, each with an expected answer/entity set/path. Must be 100% pass — a failure is a bug, not a quality score. | `evals/` | Every commit touching graph queries, NL query, or the ontology; required before increment-15 release sign-off |

## Coverage expectations

- Every source parser, entity resolution path, and query template needs a corresponding unit test before the increment implementing it is considered done — this is core deterministic logic with an enumerable input/output space, so there's no excuse for it being untested.
- Ingestion idempotency (re-running twice produces zero duplicates) needs an explicit integration test, not just an assumption.
- FR13's "explicit non-answer" behavior needs its own tests (unsupported question shape, unresolvable entity name) — it's as important to verify as the happy path.
- UI-layer HTMX/Cytoscape.js rendering is acceptable to leave to manual verification for MVP1 — no browser-automation test suite is required at this stage, given the zero-LLM, server-rendered, low-complexity UI.

## Test data policy

Synthetic-only, generated by `src/datagen/` for the fictional "Meridian Retail Group" scenario (see `docs/00_project/PROJECT_CHARTER.md` and the `synthetic-data-design` skill). Test fixtures either reuse the generated `data/sample/` files directly or use small, hand-written synthetic snippets scoped to the unit under test (e.g. a 3-record CSV fragment for a parser test) — never real company or customer data, and never data requiring anonymization (there's nothing real to anonymize).

## Definition of Done (testing)

- [ ] New/changed behavior has a corresponding test.
- [ ] Tests actually exercise the new logic, not just a smoke test.
- [ ] If the change touches ingestion or the ontology, data-quality checks still pass against a freshly re-ingested graph.
- [ ] If the change touches graph queries or NL query, the golden dataset in `evals/` still passes 100%.
- [ ] CI is green (or, for the `local_only` MVP1 delivery mode, the local test command in `docs/03_operations/RUNBOOK.md` is green before committing).
